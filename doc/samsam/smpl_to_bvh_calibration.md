# 영상 → BVH 변환 보정값 (2026-09-11)

> 목적: `hmr4d_results.pt`(GVHMR/FootMR 출력)를 Motion Puzzle 입력 BVH로 바꿀 때 쓰는 보정 상수와 fps를 한곳에 적어둔다. 클립마다 다시 판단하지 않기 위한 문서다. `data/raw`에 171개 클립이 있고 앞으로 계속 변환해야 한다.

## 1. 왜 필요한가

첫 변환(`test_video`, 2026-09-11)에서 캐릭터가 바닥을 뚫고 상하로 튀었고, 고친 뒤에는 다리를 과하게 벌리고 달렸다. 원인 세 가지였고 전부 "판단이 필요한 값"이라 여기 고정해둔다.

1. **단위** — CMU BVH는 cm가 아니라 자체 단위인데 `hmr4d_to_npz.py`가 미터→cm로 `×100`을 했다. 5.6배 과대.
2. **원점** — GVHMR의 `transl`은 절대 높이가 아니라 **첫 프레임 기준 상대 변위**다(실측 평균 0.06 m, 음수도 나옴). 바닥 높이를 더하지 않으면 캐릭터가 원점 근처에 떠 있다.
3. **쉴 때 자세** — 두 골격의 쉴 때 자세가 다른데 회전을 그대로 복사했다. 양다리가 30° 과하게 벌어졌다(3절).
4. **높이 드리프트** — GVHMR의 월드 높이 추정이 시간에 따라 밀린다. 평평한 바닥에서 뛰었는데 비탈을 올라가는 것처럼 보인다(4절).
5. **접지** — 쉴 때 자세 기준 힙 높이만으로는 동작 중 발이 바닥을 파고든다(5절).

## 2. 보정 상수

`retarget_smpl_to_cmu.py`가 `RAW31_OFFSETS`에서 직접 계산한다. 하드코딩된 매직넘버가 아니라 골격에서 유도된 값이므로, 골격이 바뀌면 자동으로 따라간다.

| 상수 | 값 | 유도 |
|---|---|---|
| `SMPL_LEG_M` | 0.82 | SMPL 템플릿 다리 길이(고관절→무릎→발목), 미터 |
| `UNITS_PER_M` | **17.865** | (대퇴 \|offs[3]\|=7.158 + 경골 \|offs[4]\|=7.492) ÷ 0.82 |
| `REST_HIP_Y` | **17.616** | 보정된 쉴 때 자세에서 FK로 계산 — 가장 낮은 관절이 바닥(y=0)에 닿는 힙 높이 |

**검증 근거**: 배율 보정 전 단계에서 오프셋 합으로 계산한 15.993이 CMU 참조 `test_bvh/41_02.bvh`의 루트 Y 최소값 **16.00**과 일치했다. 골격 유도값이 실제 CMU 데이터와 맞으므로 배율 근거가 선다. 현재 값 17.616은 여기에 쉴 때 자세 보정(3절)이 더해진 것이다 — 다리가 덜 벌어지면 발이 더 아래로 내려가므로 힙이 그만큼 높아야 한다. 단순 오프셋 합으로는 더 이상 맞지 않아 FK로 계산한다.

적용 위치는 `retarget_smpl_to_cmu.py`의 `retarget()`:

```python
positions[:, 0] = root_trans * UNITS_PER_M
positions[:, 0, 1] += REST_HIP_Y
```

단위 변환과 바닥 정렬은 **골격을 아는 쪽**이 해야 하므로 여기에 둔다. `hmr4d_to_npz.py`는 SMPL 원래 단위인 미터를 그대로 내보낸다(예전엔 여기서 ×100을 했다 — 되돌리지 말 것).

## 3. 쉴 때 자세 보정

**증상**: 뛰는 영상인데 다리를 양옆으로 벌리고 달렸다.

**원인**: CMU 골격은 쉴 때부터 다리를 각각 수직에서 20° 벌리고 어깨를 20° 올린 자세다. SMPL 템플릿은 대퇴가 5.2°, 상완이 수평에서 2.8°다. 회전만 복사하면 SMPL 회전이 0일 때 CMU 골격이 자기 쉴 때 자세로 가므로, 양다리가 **30° 과하게** 벌어진 채로 움직인다. CMU 원본 모션이 멀쩡해 보이는 건 그 데이터가 이 골격용으로 만들어져 회전값에 안쪽으로 접는 보정이 이미 들어 있기 때문이다 (`127_21.bvh` 첫 프레임 `LeftUpLeg` 회전 `[1.8, -10.7, -8.9]`).

뷰어도 이걸 못 고친다 — `samsam_viewer.html`의 `alignByBone`은 Mixamo 뼈 방향을 **CMU 방향에 맞추는** 것이라 벌어짐을 그대로 재현한다.

**보정**: 관절 j가 회전시키는 뼈의 CMU 쉴때 방향을 SMPL 쉴때 방향으로 돌리는 쿼터니언 `A_j`를 두고

```
q_cmu_local[j] = A_parent⁻¹ ∘ q_smpl_local[j] ∘ A_j
```

를 쓴다. `SMPL_REST_DIR`(20개 관절의 단위 방향 벡터)은 `SMPL/body_models/smpl/SMPL_NEUTRAL.pkl`의 템플릿 관절 위치 `J`에서 계산해 **상수로 구워 넣었다** — 런타임에는 여전히 SMPL 모델 파일이 필요 없다(라이선스).

주요 보정량: 대퇴 14.8° / 정강이 22.8° / 발 16.2° / 상완 6.7° / 요추·흉추 8.6~17.0°.

**일부러 뺀 것 (1) — 목→머리(`Neck1`, 42.3°)**: SMPL의 `head` 관절은 목보다 앞쪽에 있고(방향 Z +0.62) CMU `Head`는 거의 수직 위다. 관절 의미 자체가 다르므로 보정하면 머리가 42° 앞으로 숙여진다. 의미가 다른 건 보정이 아니라 왜곡이라 그대로 둔다.

**일부러 뺀 것 (2) — 다운스트림이 안 읽는 관절**: `LHipJoint`·`RHipJoint`·`LowerBack`·`LeftShoulder`·`RightShoulder`. Motion Puzzle이 쓰는 21관절(`SELECTED_31_TO_21`)에도, `samsam_viewer.html`의 `CMU_TO_MIXAMO`(19개)에도 없다.

여기에 보정을 넣으면 **자식의 로컬 회전에는 `A_parent⁻¹`이 들어가는데 정작 부모의 `A`는 아무도 적용하지 않아** 소비하는 쪽에서 딱 그만큼 틀어진다. 2026-09-11에 실제로 겪었다 — 양쪽 다리가 각각 23.8° / 22.9° 틀어져 Mixamo 캐릭터가 뒤꿈치로 걷는 것처럼 보였다. BVH 자체는 FK로 검증하면 멀쩡했기 때문에(파이썬 FK는 31관절을 다 쓴다) 원인 파악이 늦었다.

`retarget_smpl_to_cmu.py`에 `assert set(SMPL_REST_DIR) <= set(SELECTED_31_TO_21)` 가드를 넣어 재발을 막는다. **보정은 다운스트림이 실제로 읽는 관절에만 넣는다.**

**검증**: SMPL 회전을 전부 0으로 넣고 FK를 돌리면 보정 대상 뼈 방향이 SMPL 템플릿과 **오차 0.00°**로 일치한다. 양다리 벌어짐 합은 40.0° → **10.9°**(SMPL 템플릿 값과 동일). 검증 스크립트는 `retarget_smpl_to_cmu.py`의 자체 검증에 포함돼 있다.

## 4. 높이 드리프트 제거

**증상**: 평평한 바닥에서 뛴 영상인데 캐릭터가 계속 위로 올라간다.

**실측** (`test_video`, 354프레임 / 5.91초):

```
루트 Y 17.62 → 20.76   총 +3.05단위(+0.17 m) 상승
수평 이동 1.81 m       → 실효 경사 5.4도
추세 제거 후 잔차 −1.45 ~ +1.20   ← 실제 뛰는 상하 진폭, 정상
```

진폭 자체는 정상이고 그 위에 우상향 추세가 얹혀 있다. `-s`(정적 카메라, SLAM 생략)로 돌릴 때 월드 높이 추정이 드리프트하는 현상이다. 촬영 가이드상 바닥은 평평하므로(`samsam_shooting_guide.md`) 이 추세는 실제 움직임이 아니다.

**보정**: `retarget_smpl_to_cmu.py`의 `detrend_height()`가 루트 높이의 **선형 추세만** 뺀다(평균 높이는 유지). 기본 동작이고, `--keep-height-drift`로 끌 수 있다.

보정 후: 전체 추세 `+0.000`단위, 시작 17.62 / 끝 17.72.

**끄고 써야 하는 경우**: 클립 전체에서 높이가 실제로 변하는 동작 — 계단을 오르거나, 서서 시작해 앉은 채로 끝나는 촬영. 선형 추세 제거가 그 변화를 지워버린다. M04(앉았다 일어서기)처럼 시작·끝 높이가 같은 동작은 켜둬도 안전하다.

## 5. 접지 (바닥 붙이기)

`REST_HIP_Y`는 **쉴 때 자세**에서 계산한 값이라, 동작 중 발이 그보다 아래로 내려가는 건 고려하지 않는다. 실측에서 발가락이 바닥 아래 0.63~1.19단위(약 6 cm)까지 파고들었다(CMU 참조 `127_21.bvh`는 0.63 / −0.02).

`ground()`가 클립 전체에서 가장 낮은 발 위치(`LeftFoot`/`LeftToeBase`/`RightFoot`/`RightToeBase`)가 바닥 y=0에 오도록 루트 높이를 통째로 옮긴다. **드리프트 제거 뒤에** 적용해야 순서가 맞는다.

기본은 최저값(`percentile=0`)이라 관통이 정확히 0이 된다. 추정이 한 프레임 튀어서 클립 전체가 들리는 경우에만 올린다 — 실측(354프레임): `0` → 관통 0.000 / `0.2` → −0.040(0.2%) / `1.0` → −0.496(1.1%).

루트를 수직으로 평행이동할 뿐이라 관절 각도는 하나도 변하지 않는다(6절 충실도 검증에서 확인).

## 6. fps — 원본별 실측값

`--fps`는 `hmr4d_to_npz.py`의 **필수 인자**다(`.pt`에 fps가 안 들어 있음). 원본 파일에서 확인한 값:

| 원본 | fps | 비고 |
|---|---|---|
| `data/raw/P0xx_*.mov` | **59.94** (`60000/1001`) | 1920×1080. 참가자 촬영본 전부 |
| 루트 `A_*.MOV` | 23.976 (`24000/1001`) | 3840×2160, 초기 테스트 |
| 루트 `B_*.MOV` | 24 (`24/1`) | 3840×2160, 초기 테스트 |

**함정**: `outputs/demo/<이름>/0_input_video.mp4`의 fps를 보고 판단하면 안 된다. `tools/demo.py:110`이 `get_writer(cfg.video_path, fps=30, crf=CRF)`로 **30을 하드코딩**한다. 원본 프레임을 전부 읽어 30fps로 라벨만 다시 붙여 쓰는 것이라 프레임 수는 보존되지만 fps 값은 원본과 무관하다. 반드시 `data/raw`의 원본을 `ffprobe`로 확인할 것:

```bash
ffprobe -v error -select_streams v:0 -show_entries stream=r_frame_rate -of csv=p=0 <원본>
```

fps가 2배 틀리면 동작 속도가 2배로 어긋난다 — 스타일의 타이밍 특성이 곧 우리가 잡으려는 신호이므로 치명적이다.

## 7. 변환 절차

```bash
conda run -n motion_puzzle python hmr4d_to_npz.py \
    --pt <hmr4d_results.pt> --out smpl_pose.npz --fps 59.94
conda run -n motion_puzzle python retarget_smpl_to_cmu.py \
    --npz smpl_pose.npz --out external/motion_puzzle/datasets/cmu/uploads/<이름>.bvh
```

`uploads/`에 넣으면 `style_transfer.html`의 두 드롭다운("내 업로드" 그룹)에 자동으로 뜬다. 파일명은 `^[A-Za-z0-9_.-]+\.bvh$`만 허용된다(한글·공백·괄호 불가).

Colab 출력은 구글 드라이브가 맥에 마운트돼 있어 따로 내려받을 필요가 없다:
`~/Library/CloudStorage/GoogleDrive-<계정>/내 드라이브/samsam_footmr_checkpoints/outputs/<이름>/hmr4d_results.pt`

## 8. 변환 후 검증

### 8-0. 충실도 — SMPL 원본과 관절 각도 대조

가장 강한 검증이다. SMPL 파라미터로 직접 FK를 돌려 나온 관절 각도와 BVH의 관절 각도를 프레임마다 비교한다. 보정은 전부 골격 차이·루트 위치에 대한 것이므로 **관절 각도는 하나도 변하면 안 된다**.

2026-09-11 실측 (354프레임, 위 보정 전부 적용 후):

| 관절 | SMPL 평균 | BVH 평균 | 최대차 | 상관 |
|---|---|---|---|---|
| 왼무릎 | 138.8° | 138.8° | 0.0° | 1.000 |
| 오른무릎 | 139.5° | 139.5° | 0.0° | 1.000 |
| 왼발목 | 99.5° | 99.5° | 0.0° | 1.000 |
| 왼팔꿈치 | 83.4° | 83.4° | 0.0° | 1.000 |
| 오른팔꿈치 | 78.7° | 78.7° | 0.0° | 1.000 |

**동작이 이상해 보이는데 이 표가 0.0°로 맞는다면, 원인은 변환이 아니라 GVHMR 추정 자체이거나 그 뒤의 스타일 전이다.** GVHMR 추정은 Colab이 렌더해둔 `outputs/demo/<이름>/1_incam.mp4`(원본 영상 위에 겹쳐 렌더)로 눈으로 확인할 수 있다.

### 8-1. 루트 높이·프레임 시간

루트 Y가 CMU 참조 범위 안에 드는지 본다. 벗어나면 단위나 원점이 어긋난 것이다.

| 파일 | 루트 Y 최소~최대 | 수평 이동 X / Z |
|---|---|---|
| `127_21.bvh` (CMU 참조, 이동 많음) | 16.13 ~ 25.03 | 39 / 101 |
| `41_02.bvh` (CMU 참조, 제자리) | 16.00 ~ 16.82 | 32 / 34 |
| `test_video_20260911.bvh` (보정 전) | **−4.46 ~ 19.53** | **315 / 219** |
| `test_video_20260911.bvh` (단위·원점만 보정) | 15.20 ~ 19.48 | 56 / 39 |
| `test_video_20260911.bvh` (쉴 때 자세까지 보정) | 16.82 ~ 21.11 | 56 / 39 |
| `test_video_20260911.bvh` (높이 드리프트까지 제거) | 15.71 ~ 18.36 | 56 / 39 |
| `test_video_20260911.bvh` (접지까지, 최종) | 16.48 ~ 19.13 | 56 / 39 |

발 최저 높이도 본다 — `ground()` 적용 후 정확히 0이어야 한다(5절).

확인 스니펫:

```python
lines = open(path).read().splitlines()
i = next(k for k, l in enumerate(lines) if l.strip().startswith('Frame Time'))
print('Frame Time:', lines[i])                      # 59.94fps면 0.01668
rows = [l.split() for l in lines[i+1:] if l.strip()]
ys = [float(r[1]) for r in rows]                     # 루트 Y = 2번째 채널
print(f'루트 Y {min(ys):.2f} ~ {max(ys):.2f}')       # 대략 15~25 안이어야 정상
```

`Frame Time`이 0.01668(59.94fps)인지도 같이 본다. 0.03333이 나오면 `--fps`를 30으로 준 것이다.

루트 Y의 **선형 추세**도 확인한다 — 0에 가까워야 한다(4절):

```python
import numpy as np
t = np.arange(len(ys))
print(f'추세 {np.polyfit(t, ys, 1)[0] * len(ys):+.3f} 단위')   # 0 근처여야 정상
```

## 9. 알려진 한계 (보정으로 해결 안 됨)

`retarget_smpl_to_cmu.py` 독스트링에 있는 두 가지에 머리 방향이 더해진다.

- SMPL spine2 회전을 버린다 — 등을 크게 굽히는 동작에서 오차.
- SMPL 쇄골(collar) 회전을 버린다 — 어깨를 크게 으쓱이는 동작에서 오차. CMU 골격에 쇄골 관절이 있지만 Motion Puzzle이 쓰는 21관절에 포함되지 않아, 채워도 결과에 반영되지 않는다.
- 목→머리 방향은 보정하지 않는다(3절) — 고개 각도가 그 사람 스타일의 핵심인 동작에서는 재현되지 않는다.

스타일 레퍼런스용 클립을 고를 때 이 두 가지가 그 사람 스타일의 핵심인 동작은 피하는 편이 낫다.
