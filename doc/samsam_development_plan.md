# 쌤쌤 개발기획서 (2026-07-23)

> 배경·목표·아키텍처·일정·리스크를 한 문서로 정리한 정식 개발기획서. 팀 내부 실행 디테일(세션별 작업표, 실행 로그)은 `samsam_plan.md`에 그대로 유지하고, 이 문서는 그걸 압축·구조화한 상위 문서. 쉬운 말로 쓴 팀 공유용 요약은 `team_progress_report.md` 참고.

---

## 1. 배경

사람마다 걸음걸이·손짓·춤추는 느낌이 다르다 — "움직이는 방식"에도 그 사람만의 지문 같은 게 있지 않을까라는 질문에서 출발했다. 유튜브 댄스 챌린지 영상 5종·50여 개를 관절 움직임만 뽑아 DTW로 비교한 실험에서 "같은 동작도 사람마다 다르다"는 확인했지만, 원래 방향(움직임으로 개인 식별 → 생체 자산화)에는 두 벽이 있었다:

- **기술 벽**: 같은 사람의 일관성이 아직 통계로 증명 안 됨 (상황이 바뀌면 숫자가 흩어짐).
- **법 벽**: "움직이는 방식"을 소유·거래할 법적 근거가 아직 없음.

그래서 "당신인지 알아맞히기"에서 "당신의 움직임 느낌을 뽑아서 캐릭터에 입히기"로 방향을 틀었다 — **쌤쌤**. 통계 증명이 아니라 결과물이 눈에 보이면 되고, 창작자(게임·애니·버추얼 캐릭터·광고)라는 명확한 수요가 있으며, 필요한 기술은 전부 공개된 것을 조립하면 된다는 게 핵심 전환 논리다. 자세한 경위는 `team_progress_report.md` 1~4절.

## 2. 목표

### 2-1. 코어 목표 (캡스톤 필수)
**"같은 동작이 사람마다 다른 결로 움직인다"를 웹 뷰어에서 눈으로 보여준다.** 촬영한 여러 사람의 움직임 "스타일"을 추출해 임의의 콘텐츠 동작에 입히고, 결과가 사람마다 다르게 보이는 것을 DTW·ICC로 정량 검증 + 웹에서 육안 확인한다.

### 2-2. 확장 목표 (조건부, 세션 7 후보)
스타일 입힌 스켈레톤에 카메라 각도를 얹어 영상으로 뽑고, 그걸 포즈 기반 AI 영상 생성 모델에 넣었을 때 카메라 앵글이 실제 결과물에 반영되는지 확인한다. 세션 6까지 끝난 뒤 팀이 정식 편입 여부를 결정하는 **곁가지 스파이크**이며, 실패해도 코어 완성 데모에는 영향 없다.

### 2-3. 원칙 (전 구간 적용)
1. **조립이지 연구가 아니다** — 사전학습·공개 코드만 사용, 처음부터 학습 금지.
2. **캡스톤 코어는 하나** — 플랫폼·디지털트윈·광고영상은 발표 포장이며 기술개발 시간을 먹지 않는다.
3. **성공 기준은 소박하게 고정** — 큰 패턴(리듬·보폭·무게중심)까지만 약속, 손가락·감정 뉘앙스는 범위 밖.

## 3. 기술 아키텍처 (파이프라인)

```
[촬영]                [2D 포즈]        [2D→3D + 발보정]      [스타일 전이]        [리타겟]            [렌더/뷰어]
단안 RGB 고정카메라  →  MediaPipe Pose →  GVHMR + FootMR   →  Motion Puzzle    →  SMPL→Mixamo      →  three.js
8동작×8-12인          (로컬, 무료)        (Colab, 1세션)       (로컬 Mac, 사전학습)  (Aberman retarget)   (OrbitControls,
                                                                                                        before/after)
                                                                                                             │
                                                                                                             ▼
                                                                                                  [평가] DTW·ICC 정량검증
```

**확장(세션 7 후보) — 코어 파이프라인 뒤에 선택적으로 붙는 가지:**
```
three.js 카메라 경로 선택 → 구동 포즈 영상 렌더(DWPose 포맷, draw_pose() 직접 호출)
  → MusePose(1순위) 또는 MimicMotion(2순위) + 레퍼런스 캐릭터 이미지
  → AI 생성 영상 → 카메라 각도가 반영됐는지 육안 게이트 판정
```

| 단계 | 도구 | 선정 근거 (요약) |
|---|---|---|
| 촬영 | 단안 RGB, 삼각대 고정 | 멀티캠 대비 촬영 로지스틱스 최소(1인당 15-20분). `samsam_shooting_guide.md` |
| 2D 포즈 | MediaPipe Pose | 이미 로컬 venv에 있음, 무료, 세션 없이 즉시 |
| 2D→3D | **GVHMR** | FootMR이 GVHMR 코드베이스를 그대로 포크한 것으로 확인(2026-07-23) — WHAM/MediaPipe를 골랐으면 FootMR용 글루 코드가 별도로 필요해 "조립" 원칙 위반. 정확도·속도도 WHAM보다 우세. |
| Footskate 보정 | FootMR | GVHMR과 같은 Colab 세션에서 이어서 실행(환경 셋업 1회로 충분) |
| 스타일 전이 | **Motion Puzzle** | motion-to-motion(텍스트 아님), Mac 로컬 CPU 실행 가능, 2026-07-15 스파이크에서 스타일 분리·콘텐츠 보존 모두 게이트 통과 |
| 리타겟 (2단계) | SMPL→CMU(`smpl2bvh`+커스텀 스크립트) → [스타일 전이] → CMU→Mixamo(Aberman `deep-motion-editing`) | Motion Puzzle·three.js가 서로 다른 스켈레톤을 요구해 리타겟이 앞뒤로 한 번씩 필요함을 2026-07-23 코드 확인으로 재확인. SMPL→CMU 구간은 사전학습 도구가 없어 커스텀 스크립트 필요(`samsam_dev_spec.md` 1절). footskate/관통 보이면 H4(papers.md) 검토 |
| 렌더/뷰어 | three.js | OrbitControls로 카메라 각도 조작이 그냥 내장 기능 — 별도 개발 불필요 |
| 평가 | DTW·ICC (기존 `analyze.py`) | 식별 트랙에서 이미 만든 자산 재사용 |
| [확장] 카메라 구동영상 | DWPose 포맷 렌더 스크립트 | MimicMotion/Moore-AnimateAnyone/MusePose 전부 OpenPose 아닌 DWPose 사용(2026-07-23 확인) |
| [확장] AI 영상 생성 | **MusePose** | MIT 라이선스, T4 VRAM(16GB@512×512×48프레임)에 4개 후보 중 가장 근접, 자체 pose-align 도구 보유 |
